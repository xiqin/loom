# 常见误区 vs 现实

## 完整对照表

| 误区 | 现实 | 正确做法 |
|--------|---------|----------|
| "太简单了不需要测试" | 简单的代码也会崩溃。测试需要 30 秒。 | 写测试，保护未来。 |
| "实现都写完了，测试随便补补" | 随便补的测试只覆盖 happy path，漏掉边界和异常。 | 逐个 behavior 对照补测，覆盖正常/异常/边界。 |
| "已经手动测试过了" | 临时 ≠ 系统。没有记录，无法重新运行。 | 自动化测试，可以重复运行。 |
| "跳过重构直接写测试更快" | 测试会锁死当前结构。凌乱实现被测试锁住后更难改。 | 先重构再写测试，让测试锁定值得锁定的结构。 |
| "为了让代码好测，加个构造参数注入依赖" | 这就是 test-induced design damage。生产代码不该为测试而改结构。 | 用真实依赖（mkdtempSync、内存 DB），不为测试加接口。 |
| "测试很难写 = 设计不清晰" | 可能是，也可能是你在测内部实现而非 public boundary。 | 确认 seam，通过 public API 测，不测内部状态。 |
| "覆盖率到了 90% 就够了" | 覆盖率数字无意义。关键是未测试的区域是否有可错路径。 | 查看未覆盖区域，逐项判断是否需要补测。 |
| "现有代码没有测试" | 你在改进它。为现有代码添加测试。 | 改进代码，添加测试。 |
| "测试太难写，改改生产代码吧" | 如果改生产代码是为可测试性而非业务需求，方向错了。 | 先确认是否在测内部实现；若 seam 正确但确实难测，再考虑设计。 |
| "手动测试更快" | 手动不能证明边界情况。每次更改你都会重新测试。 | 自动化，一次编写，终身受益。 |

## 关键原则

1. **实现先行**，测试验证真实 public API。
2. **重构在测试前**，测试锁定值得锁定的结构。
3. **覆盖率是发现工具**，不是达标指标。

## 记住

- 测试通过的代码 ≠ 工作正常的代码。
- 测试失败的代码 = 有问题的代码。
- 实现后写的测试 = 你知道测的是已成型的真实接口。
- **不为测试改设计，设计服务于业务。**
